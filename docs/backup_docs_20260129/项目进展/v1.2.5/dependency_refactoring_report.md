# SQLCC依赖关系重构报告

## 重构时间
2025-12-21 03:24:00 (UTC+8)

## 重构概述

根据前期分析发现的依赖关系问题，本次重构旨在从源头上解决循环引用和依赖方向违规问题，提高代码库的可维护性和架构清晰度。

## 已完成工作

### 1. 库命名统一 (2025-12-21 03:24:00)
- **问题**: SQL解析器库命名不一致，存在 `sqlcc_parser` 和 `sql_parser` 两种命名
- **解决**: 统一使用 `sql_parser` 作为标准库名
- **修改文件**:
  - `src/sql_parser/BUILD.bazel`: 主库名改为 `sql_parser`
  - 批量更新所有BUILD.bazel文件中的引用
- **影响**: 消除了命名不一致导致的依赖解析问题

### 2. 依赖关系分析框架建立
- **分析工具**: 基于includes.txt的依赖图构建
- **检测能力**:
  - 循环引用检测
  - 依赖方向违规检查
  - 组件耦合度分析
- **分析结果**: 识别出多个关键问题点

## 当前架构层次结构

```
高层 (High Level)
├── execution (查询执行层)
├── network (网络通信层)
└── core (核心业务逻辑层)
    ├── sql_parser (SQL解析层)
    ├── database_manager (数据库管理层)
    └── storage_engine (存储引擎层)
        └── storage (存储组件层)
            └── utils (工具库层)
```

**依赖规则**: 只能上层依赖下层，不允许反向依赖。

## 待解决的关键问题

### 1. 循环依赖问题
根据分析发现的循环引用需要逐步消除：
- 核心组件间的循环引用
- 存储引擎内部的循环依赖
- 执行器与解析器的循环引用

### 2. 依赖方向违规
发现多处高层组件依赖低层组件的情况：
- execution组件引用storage组件
- network组件引用core组件
- 违反了依赖层次规则

### 3. 组件职责不清
某些组件承担了过多职责，导致耦合度过高：
- core组件过于庞大
- storage_engine与storage组件边界不清
- utils组件被过多依赖

## 重构策略

### 阶段1: 紧急修复 (当前进行中)
1. **修复Bazel构建配置**
   - 移除不支持的`allow_empty`参数
   - 修复不存在的头文件库引用
   - 统一库命名规范

2. **消除简单循环依赖**
   - 使用前向声明减少include依赖
   - 重构类层次结构
   - 引入接口类分离实现

### 阶段2: 架构重构 (计划中)
1. **组件职责分离**
   - 核心组件功能拆分
   - 存储引擎架构优化
   - 执行器职责明确

2. **依赖注入模式**
   - 引入依赖注入容器
   - 减少直接依赖关系
   - 提高组件可测试性

### 阶段3: 接口抽象 (后续)
1. **接口层设计**
   - 为主要组件定义接口
   - 实现插件化架构
   - 支持组件热替换

2. **配置驱动**
   - 基于配置的组件装配
   - 运行时依赖解析
   - 提高系统灵活性
