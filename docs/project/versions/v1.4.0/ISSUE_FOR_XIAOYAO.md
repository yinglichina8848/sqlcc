## 四、对抗式改进流程

### 4.1 流程设计

**李哥的管理艺术**：用对抗式的方法提高质量

```
1. Gemini (审查者) → 提出 Issue，找出问题
   ↓
2. Claude Code (执行者) → 修复 Issue
   ↓
3. Gemini (审查者) → 评审修复结果，给出分数
   ↓
4. 分数 >= 80? → 是 → 关闭 Issue
   ↓ 否
5. 返回步骤 2，继续修复
```

### 4.2 不同 AI 的目标

| AI | 角色 | 目标 |
|-----|------|------|
| **Gemini** | 资深架构师 | 严格审查，找出问题 |
| **Claude Code** | 专业工程师 | 高效修复，完成任务 |
| **OpenCode** | 专业工程师 | 代码实现 |
| **高小原** | 项目经理 | 控制流程，协调 AI |
| **高小药** | 学习者 | 阅读文档，学习方法 |

### 4.3 实际效果

**第一轮对抗** (Issue #001):

```
1. Gemini 审查 → 75 分
2. Claude Code 修复
3. Gemini 复审 → 80+ 分 ✅
4. Issue #001 关闭
```

**耗时**: 约 10 分钟

### 4.4 评分标准

| 分数 | 说明 |
|------|------|
| 100 | 完美，无需改进 |
| 90 | 优秀，只需小改进 |
| **80** | **良好，达到合并标准** |
| 70 | 一般，需要改进 |
| <60 | 不及格，需要重做 |

## 五、正确的 Git 分支管理

### 5.1 分支结构

```
main (主分支)
  ↑
feature (功能分支)
  ↑
feature/docs-improvement-v1.4.0 (文档改进)
  ↑
feature/ibufferpool-interface (接口重构)
```

### 5.2 正确的合并路径

| 源分支 | 目标分支 | 是否正确 |
|--------|---------|---------|
| feature/docs-improvement-v1.4.0 | feature | ✅ 正确 |
| feature/docs-improvement-v1.4.0 | main | ❌ 错误 |

### 5.3 我之前犯的错误

| 错误做法 | 李哥的批评 |
|---------|-----------|
| 直接合并到 main | "不要动 main 分支" |
| 跨 PR 开发 | "完成一个 PR 之后再开启下一个" |
| 同时做文档和代码 | "不要让 AI CLI 身兼多职" |

### 5.4 正确的做法

1. **只在工作分支上工作**
2. **PR 合并到上一级分支**
3. **等李哥决定是否提升 baseline**
4. **最后才合并到 main**
