## 🤖 AI 必须遵从的原则

### 1. 理解上下文原则
**原则描述**: AI 在执行任何操作之前，必须先全面理解项目上下文，包括：
- 项目架构和模块依赖关系
- 现有代码风格和编码规范
- 当前问题和已知限制
- 版本目标和约束条件

**具体要求**:
- 在修改任何文件之前，必须先使用 `read_file` 工具读取文件内容
- 必须使用 `search_file_content` 或 `glob` 工具了解代码结构
- 必须参考 AGENTS.md 中的项目规范
- 必须查看相关模块的现有实现

**禁止行为**:
- ❌ 不读取文件直接修改代码
- ❌ 不了解上下文就提出解决方案
- ❌ 不考虑项目风格就编写代码

---

### 2. 系统性分析原则
**原则描述**: AI 必须进行系统性的分析，而不是盲目试错。必须先识别问题、分析原因、制定计划，然后执行。

**具体要求**:
- 使用 `task` 工具进行系统性探索和分析
- 生成详细的分析报告，包括：
  - 问题分类和统计
  - 根本原因分析
  - 系统性解决方案
  - 实施路线图
  - 风险评估

**禁止行为**:
- ❌ 不分析就直接修改代码
- ❌ 不考虑影响范围就进行修改
- ❌ 不进行风险评估就执行变更

---

### 3. 分级处理原则
**原则描述**: AI 必须按照问题的严重级别和优先级进行分级处理，优先解决 Critical 和 High 级别的问题。

**具体要求**:
- **Critical（严重）**: 阻塞测试运行的问题，必须立即处理
- **High（高）**: 影响测试质量的问题，必须优先处理
- **Medium（中）**: 影响测试完整性的问题，按计划处理
- **Low（低）**: 改进建议，按时间安排处理

**禁止行为**:
- ❌ 不按优先级处理问题
- ❌ 跳过 Critical 问题去解决 Low 问题
- ❌ 同时处理多个不同优先级的问题

---

### 4. 代码审查原则
**原则描述**: AI 在修改代码之前，必须进行全面的代码审查，确保代码符合项目规范。

**具体要求**:
- 检查命名规范（PascalCase, snake_case, UPPER_SNAKE_CASE）
- 检查包含顺序（对应头文件、项目头、第三方头、系统头）
- 检查异常处理（使用正确的异常类）
- 检查内存管理（使用智能指针，避免内存泄漏）
- 检查线程安全（使用适当的同步机制）

**禁止行为**:
- ❌ 引入新的编码风格
- ❌ 不遵守现有代码风格
- ❌ 不考虑异常处理
- ❌ 不检查内存泄漏

---

### 5. 测试验证原则
**原则描述**: AI 在修改代码后，必须进行全面的测试验证，确保所有测试通过。

**具体要求**:
- 必须运行 `bazel test` 验证测试通过
- 必须运行 `bazel build` 验证编译通过
- 必须检查覆盖率数据是否提升
- 必须验证没有引入副作用

**禁止行为**:
- ❌ 不测试就认为代码正确
- ❌ 不验证覆盖率就认为任务完成
- ❌ 不检查副作用就提交代码

---

### 6. 文档更新原则
**原则描述**: AI 在完成任务后，必须更新相关文档，确保文档与代码同步。

**具体要求**:
- 更新 WORKLOG.md 记录工作进度
- 更新 TODO.md 标记完成的任务
- 更新 CHANGELOG.md 记录变更
- 更新分析报告反映最新状态

**禁止行为**:
- ❌ 不更新文档就认为任务完成
- ❌ 文档与代码不一致
- ❌ 遗漏重要的变更记录

---

### 7. 风险控制原则
**原则描述**: AI 在执行任何修改时，必须进行风险评估，并采取适当的控制措施。

**具体要求**:
- 在修改核心模块之前，必须先创建备份
- 在大规模重构之前，必须先进行小规模验证
- 在修改测试代码时，必须确保不影响现有测试
- 在删除文件之前，必须先确认不再需要

**禁止行为**:
- ❌ 不评估风险就进行大规模修改
- ❌ 不创建备份就删除重要文件
- ❌ 不验证影响范围就进行重构

---

### 8. 沟一风格原则
**原则**:
- 遵循项目现有的编码风格
- 参考现有代码的实现模式
- 使用项目统一的命名规范

**禁止**:
- 引入新的编码风格
- 不考虑现有代码风格
- 不统一命名规范

### 9. 最小化变更原则
**原则**:
- 只修改必要的文件
- 只修复必要的问题
- 只添加必要的测试

**禁止**:
- 不必要的重构
- 过度的修改
- 无关的变更

### 10. 持续改进原则
**原则**:
- 定期评估改进效果
- 根据反馈调整计划
- 持续优化测试覆盖率

**禁止**:
- 不评估改进效果
- 不根据反馈调整计划
- 不持续优化测试

## 📋 工作流程

### 1. 问题识别阶段
```
1. 使用 explore-agent 分析代码库
2. 识别问题和影响范围
3. 分类问题严重级别
4. 生成分析报告
```

### 2. 计划制定阶段
```
1. 根据分析报告制定解决方案
2. 按优先级排序任务
3. 制定实施路线图
4. 评估风险和预期效果
```

### 3. 实施阶段
```
1. 按照 P0 → P1 → P2 → P3 的优先级顺序执行
2. 每完成一个任务，更新 TODO.md
3. 每完成一个任务，更新 WORKLOG.md
4. 每完成一个里程碑，更新质量指标
```

### 4. 验证阶段
```
1. 运行 `bazel test` 验证测试通过
2. 运行 `bazel build` 验证编译通过
3. 收集覆盖率数据并分析
4. 更新 CHANGELOG.md 记录变更
```

### 5. 反馈阶段
```
1. 根据测试结果调整计划
2. 根据覆盖率数据优化测试
3. 根据反馈改进实现
4. 持续优化直到达到目标
```

## 🔧 工具使用指南

### 常用工具

| 工具 | 用途 | 使用场景 |
|------|------|---------|
| `read_file` | 读取文件内容 | 修改代码前必须使用 |
| `write_file` | 写入文件内容 | 创建新文件或覆盖现有文件 |
| `replace` | 替换文件内容 | 修复代码时必须使用 |
| `search_file_content` | 搜索文件内容 | 查找代码模式和依赖关系 |
| `glob` | 查找文件 | 定位需要修改的文件 |
| `run_shell_command` | 执行命令 | 运行测试和构建 |

### 常用命令

| 命令 | 用途 | 使用场景 |
|------|------|---------|
| `bazel test //tests/...` | 运行所有测试 | 验证测试通过 |
| `bazel build //src/...` | 编译源码 | 验证编译通过 |
| `bazel coverage //tests/...` | 收集覆盖率数据 | 分析测试覆盖率 |
| `bazel clean` | 清理构建缓存 | 重新构建前必须执行 |
