## 4.0 架构设计基础概念：软件架构设计的入门指南

在深入DBMS架构设计之前，我们需要先理解什么是架构设计，以及为什么架构设计对软件开发如此重要。

### 4.0.1 什么是架构设计？

#### 架构设计的定义

**架构设计**是软件系统的高层结构设计，它关注系统的整体组织、组件之间的关系、以及如何满足系统的功能性和非功能性需求。

**生活中的类比**：
- **建筑架构**：在建造房子之前，建筑师需要设计房子的整体结构（地基、承重墙、楼层数、房间布局），而不是直接开始砌砖
- **软件架构**：在编写代码之前，软件架构师需要设计系统的整体结构（模块划分、组件关系、数据流向），而不是直接开始写代码

#### 架构设计与详细设计的区别

```
┌─────────────────────────────────────────────────────────┐
│                   软件开发过程                           │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  1. 需求分析                                             │
│     - 用户需要什么功能？                                 │
│     - 系统的性能、安全、可用性要求是什么？              │
│                                                         │
│  2. 架构设计 ←─── 本章重点讲解                          │
│     - 系统整体结构是什么？                               │
│     - 如何划分模块和组件？                               │
│     - 组件之间如何协作？                                 │
│     - 如何满足非功能性需求？                             │
│                                                         │
│  3. 详细设计                                             │
│     - 每个模块的内部结构如何设计？                       │
│     - 函数和类的接口如何定义？                           │
│     - 数据结构如何选择？                                 │
│                                                         │
│  4. 编码实现                                             │
│     - 编写具体的代码                                     │
│     - 单元测试和集成测试                                 │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**表格对比**：

| 维度 | 架构设计 | 详细设计 |
|-----|---------|---------|
| **关注点** | 系统整体结构 | 模块内部实现 |
| **抽象层次** | 高层抽象 | 低层具体 |
| **时间点** | 项目早期 | 编码前期 |
| **输出** | 架构图、设计文档 | 类图、接口定义 |
| **影响范围** | 整个系统 | 单个模块 |

### 4.0.2 为什么需要架构设计？

#### 问题1：没有架构设计会怎样？

**场景：开发一个学生管理系统**

**没有架构设计的情况**：
```c
// 所有代码都在一个文件中
// student_management.c
#include <stdio.h>
#include <string.h>

struct Student {
    int id;
    char name[100];
    int age;
    char major[100];
};

// 全局变量（混乱）
struct Student students[1000];
int student_count = 0;
FILE* log_file;

// 混乱的函数
void add_student() { /* ... */ }
void delete_student() { /* ... */ }
void search_student() { /* ... */ }
void save_to_file() { /* ... */ }
void load_from_file() { /* ... */ }
void log_operation() { /* ... */ }
// ... 更多函数

int main() {
    // 所有逻辑混在一起
    int choice;
    while (1) {
        printf("1. Add student\n");
        printf("2. Delete student\n");
        printf("3. Search student\n");
        scanf("%d", &choice);
        
        if (choice == 1) {
            add_student();
        } else if (choice == 2) {
            delete_student();
        } else if (choice == 3) {
            search_student();
        }
    }
}
```

**问题**：
1. **难以维护**：所有代码混在一起，修改一个功能可能影响其他功能
2. **难以扩展**：添加新功能需要修改大量现有代码
3. **难以测试**：无法独立测试某个功能模块
4. **难以理解**：新人接手项目时很难理解代码结构
5. **难以协作**：多人协作时容易产生冲突

**有架构设计的情况**：
```cpp
// 清晰的模块划分
// student_management/

// student_manager.h
#ifndef STUDENT_MANAGER_H
#define STUDENT_MANAGER_H

#include "student.h"
#include "student_storage.h"
#include "logger.h"

class StudentManager {
public:
    StudentManager(IStudentStorage* storage, ILogger* logger);
    
    // 学生管理功能
    bool addStudent(const Student& student);
    bool deleteStudent(int studentId);
    Student* findStudent(int studentId);
    std::vector<Student> getAllStudents();
    
private:
    IStudentStorage* storage_;  // 存储接口
    ILogger* logger_;           // 日志接口
};

#endif

// student.h
#ifndef STUDENT_H
#define STUDENT_H

struct Student {
    int id;
    std::string name;
    int age;
    std::string major;
    
    // 转换为字符串
    std::string toString() const;
};

#endif

// student_storage.h
#ifndef STUDENT_STORAGE_H
#define STUDENT_STORAGE_H

#include "student.h"

// 存储接口（抽象基类）
class IStudentStorage {
public:
    virtual ~IStudentStorage() = default;
    virtual bool save(const Student& student) = 0;
    virtual bool load(int studentId, Student& student) = 0;
    virtual bool remove(int studentId) = 0;
};

// 具体存储实现：文件存储
class FileStudentStorage : public IStudentStorage {
public:
    explicit FileStudentStorage(const std::string& filename);
    
    bool save(const Student& student) override;
    bool load(int studentId, Student& student) override;
    bool remove(int studentId) override;
    
private:
    std::string filename_;
};

// 具体存储实现：数据库存储
class DatabaseStudentStorage : public IStudentStorage {
public:
    explicit DatabaseStudentStorage(const std::string& connection_string);
    
    bool save(const Student& student) override;
    bool load(int studentId, Student& student) override;
    bool remove(int studentId) override;
    
private:
    std::string connection_string_;
};

// logger.h
#ifndef LOGGER_H
#define LOGGER_H

// 日志接口
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& message) = 0;
};

// 具体日志实现：控制台日志
class ConsoleLogger : public ILogger {
public:
    void log(const std::string& message) override;
};

// 具体日志实现：文件日志
class FileLogger : public ILogger {
public:
    explicit FileLogger(const std::string& filename);
    
    void log(const std::string& message) override;
    
private:
    std::string filename_;
};
```

**架构设计的优势**：
1. **清晰的结构**：代码按功能模块组织，职责明确
2. **易于维护**：修改某个功能只需修改对应的模块
3. **易于扩展**：添加新功能（如数据库存储）只需实现新的接口
4. **易于测试**：可以独立测试每个模块
5. **易于理解**：新人可以通过架构图快速理解系统结构
6. **易于协作**：不同人员可以并行开发不同模块

### 4.0.3 架构设计的基本原则

#### 原则1：单一职责原则（Single Responsibility Principle - SRP）

**定义**：一个模块或类应该只有一个引起它变化的原因。

**应用场景**：数据库管理系统中，每个模块只负责一个功能领域

**反例**：
```cpp
// 违反SRP原则：一个类负责太多功能
class DatabaseManager {
public:
    // 数据管理
    void insertData(const std::string& data);
    void deleteData(int id);
    
    // 用户管理
    void createUser(const std::string& username);
    void deleteUser(const std::string& username);
    
    // 日志管理
    void writeLog(const std::string& message);
    
    // 网络管理
    void startServer();
    void stopServer();
    
    // 权限管理
    void grantPermission(const std::string& permission);
    void revokePermission(const std::string& permission);
};
```

**正例**：
```cpp
// 符合SRP原则：每个类只负责一个功能
class DataManager {
public:
    void insertData(const std::string& data);
    void deleteData(int id);
};

class UserManager {
public:
    void createUser(const std::string& username);
    void deleteUser(const std::string& username);
};

class LogManager {
public:
    void writeLog(const std::string& message);
};

class NetworkManager {
public:
    void startServer();
    void stopServer();
};

class PermissionManager {
public:
    void grantPermission(const std::string& permission);
    void revokePermission(const std::string& permission);
};
```

**优势**：
- 易于理解：每个类的职责清晰
- 易于维护：修改某个功能只需修改对应的类
- 易于测试：可以独立测试每个类

#### 原则2：开闭原则（Open-Closed Principle - OCP）

**定义**：软件实体（类、模块、函数等）应该对扩展开放，对修改关闭。

**应用场景**：数据库系统需要支持新的SQL语句类型，而不需要修改现有代码

**反例**：
```cpp
// 违反OCP原则：每次添加新语句类型都需要修改现有代码
class SQLExecutor {
public:
    void execute(const std::string& sql) {
        if (sql.find("SELECT") == 0) {
            executeSelect(sql);
        } else if (sql.find("INSERT") == 0) {
            executeInsert(sql);
        } else if (sql.find("UPDATE") == 0) {
            executeUpdate(sql);
        } else if (sql.find("DELETE") == 0) {
            executeDelete(sql);
        } else if (sql.find("CREATE") == 0) {
            // 添加新的CREATE语句类型，需要修改这里
            executeCreate(sql);
        }
        // ... 每次添加新类型都要修改这里
    }
};
```

**正例**：
```cpp
// 符合OCP原则：使用策略模式，添加新类型只需新增策略
class ExecutionStrategy {
public:
    virtual ~ExecutionStrategy() = default;
    virtual void execute(const std::string& sql) = 0;
};

class SelectStrategy : public ExecutionStrategy {
public:
    void execute(const std::string& sql) override {
        // SELECT语句的执行逻辑
    }
};

class InsertStrategy : public ExecutionStrategy {
public:
    void execute(const std::string& sql) override {
        // INSERT语句的执行逻辑
    }
};

class CreateStrategy : public ExecutionStrategy {
public:
    void execute(const std::string& sql) override {
        // CREATE语句的执行逻辑
    }
};

// 添加新类型只需创建新的策略类，无需修改现有代码
```

#### 原则3：依赖倒置原则（Dependency Inversion Principle - DIP）

**定义**：高层模块不应该依赖低层模块，两者都应该依赖抽象。

**应用场景**：数据库执行器依赖具体的存储实现

**反例**：
```cpp
// 违反DIP原则：高层模块直接依赖低层模块
class QueryExecutor {
public:
    void executeQuery(const std::string& query) {
        // 直接依赖具体的文件存储
        FileStorage storage("data.db");
        storage.write(query);
    }
};
```

**正例**：
```cpp
// 符合DIP原则：高层模块依赖抽象接口
class QueryExecutor {
public:
    QueryExecutor(IStorage* storage) : storage_(storage) {}
    
    void executeQuery(const std::string& query) {
        storage_->write(query);
    }
    
private:
    IStorage* storage_;  // 依赖抽象接口
};

// 存储接口
class IStorage {
public:
    virtual ~IStorage() = default;
    virtual void write(const std::string& data) = 0;
};

// 具体实现
class FileStorage : public IStorage {
public:
    void write(const std::string& data) override {
        // 文件存储实现
    }
};

class DatabaseStorage : public IStorage {
public:
    void write(const std::string& data) override {
        // 数据库存储实现
    }
};
```

**优势**：
- 灵活性：可以轻松替换不同的存储实现
- 可测试性：可以使用模拟对象进行单元测试
- 可维护性：修改低层实现不影响高层模块

## 4.1 从需求分析到架构设计：数据库系统的演进历程

现在我们回到数据库管理系统，看看它的架构是如何从需求分析一步步演进出来的。

### 4.1.1 数据库系统的需求分析

数据库系统是为了解决什么问题而诞生的？

#### 历史背景：从手工管理到自动化管理

**场景1：手工管理数据（1950年代）**

```
图书馆卡片目录系统：
- 每本书一张卡片
- 卡片包含书名、作者、ISBN等信息
- 查找一本书需要翻阅大量卡片
- 添加新书需要手工制作卡片
- 借还书需要手工记录
```

**问题**：
- 查找效率低
- 维护困难

**策略模式的实现细节**：

```cpp
// 1. 定义抽象基类：ExecutionStrategy
class ExecutionStrategy {
public:
    virtual ~ExecutionStrategy() = default;
    
    // 统一的执行接口
    virtual ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) = 0;
    
    // 统一的权限检查接口
    virtual bool checkPermission(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
    
    // 统一的验证接口
    virtual bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
    
    // 策略标识
    virtual std::string getStrategyName() const = 0;
};

// 2. 实现具体策略：SELECT执行策略
class SelectExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        auto selectStmt = dynamic_cast<SelectStatement*>(stmt.get());
        
        // SELECT语句特有的执行逻辑
        return executeSelect(selectStmt, context);
    }
    
    bool checkPermission(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) override {
        
        // SELECT语句的权限检查
        return hasReadPermission(context);
    }
    
    bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) override {
        
        // SELECT语句的验证逻辑
        return validateSelect(stmt, context);
    }
    
    std::string getStrategyName() const override {
        return "SelectExecutionStrategy";
    }
    
private:
    ExecutionResult executeSelect(SelectStatement* stmt, ExecutionContext& context);
};

// 3. 实现具体策略：INSERT执行策略
class InsertExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        auto insertStmt = dynamic_cast<InsertStatement*>(stmt.get());
        
        // INSERT语句特有的执行逻辑
        return executeInsert(insertStmt, context);
    }
    
    // ... 其他方法
};

// 4. 统一执行器：策略的选择和执行
class UnifiedExecutor : public ExecutionStrategy {
public:
    UnifiedExecutor() {
        // 注册所有执行策略
        strategies_[Statement::SELECT] = 
            std::make_unique<SelectExecutionStrategy>();
        strategies_[Statement::INSERT] = 
            std::make_unique<InsertExecutionStrategy>();
        strategies_[Statement::UPDATE] = 
            std::make_unique<UpdateExecutionStrategy>();
        strategies_[Statement::DELETE] = 
            std::make_unique<DeleteExecutionStrategy>();
        // ... 更多策略
    }
    
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        // 根据语句类型选择策略
        auto strategy = strategies_[stmt->getType()];
        
        // 委托给具体策略执行
        return strategy->execute(std::move(stmt), context);
    }
    
private:
    std::unordered_map<Statement::Type, 
                       std::unique_ptr<ExecutionStrategy>> strategies_;
};
```

```cpp
// 1. 在基类中定义执行流程模板
class ExecutionStrategy {
public:
    // 模板方法：定义执行流程的骨架
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) {
        
        // 步骤1：权限检查（所有语句都需要）
        if (!checkPermission(*stmt, context)) {
            return createErrorResult("Permission denied");
        }
        
        // 步骤2：语句验证（所有语句都需要）
        if (!validate(*stmt, context)) {
            return createErrorResult("Statement validation failed");
        }
        
        // 步骤3：执行准备（可选，部分语句需要）
        prepareExecution(context);
        
        // 步骤4：语句执行（必须实现，由子类提供）
        ExecutionResult result = executeStatement(stmt, context);
        
        // 步骤5：结果封装（可选，部分语句需要）
        ExecutionResult finalResult = postProcessResult(result);
        
        // 步骤6：资源清理（所有语句都需要）
        cleanupExecution(context);
        
        return finalResult;
    }
    
    // 抽象方法：必须由子类实现
    virtual ExecutionResult executeStatement(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) = 0;
    
    // 钩子方法：子类可以选择性重写
    virtual bool checkPermission(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
    
    virtual bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
    
    virtual void prepareExecution(ExecutionContext& context) {
        // 默认实现：不做任何准备
    }
    
    virtual ExecutionResult postProcessResult(
        const ExecutionResult& result) {
        // 默认实现：不做任何后处理
        return result;
    }
    
    virtual void cleanupExecution(ExecutionContext& context) {
        // 默认实现：不做任何清理
    }
    
protected:
    // 辅助方法
    ExecutionResult createErrorResult(const std::string& message) {
        ExecutionResult result;
        result.setSuccess(false);
        result.setErrorMessage(message);
        return result;
    }
    
    ExecutionResult createSuccessResult(const std::string& message = "") {
        ExecutionResult result;
        result.setSuccess(true);
        result.setMessage(message);
        return result;
    }
};

// 2. 子类实现具体步骤
class SelectExecutionStrategy : public ExecutionStrategy {
public:
    // 实现必须的抽象方法
    ExecutionResult executeStatement(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        auto selectStmt = dynamic_cast<SelectStatement*>(stmt.get());
        
        // SELECT语句的执行逻辑
        return executeSelect(selectStmt, context);
    }
    
    // 实现权限检查
    bool checkPermission(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) override {
        
        // SELECT语句需要读取权限
        return hasReadPermission(context);
    }
    
    // 实现语句验证
    bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) override {
        
        // 验证SELECT语句的有效性
        return validateSelect(stmt, context);
    }
    
    // 重写可选的钩子方法
    void prepareExecution(ExecutionContext& context) override {
        // SELECT语句需要准备聚合引擎
        context.setAggregateEngine(createAggregateEngine());
    }
    
    ExecutionResult postProcessResult(
        const ExecutionResult& result) override {
        // SELECT语句需要对结果进行排序和分页
        return sortAndPaginateResult(result);
    }
    
    void cleanupExecution(ExecutionContext& context) override {
        // 清理聚合引擎
        context.clearAggregateEngine();
    }
};
```

### 4.1.2 策略模式在DBMS架构中的设计价值

策略模式(Strategy Pattern)是SQLCC架构设计的核心模式，它将SQL语句的执行算法抽象为独立的策略类，实现了算法的可替换性和扩展性。

#### 策略模式的经典定义

策略模式定义了一系列算法，将每个算法封装起来，并使它们可以相互替换。该模式让算法独立于使用它的客户而变化。

#### SQLCC中的策略模式应用

在SQLCC中，策略模式通过`ExecutionStrategy`抽象基类实现：

**源码位置**: `/home/liying/sqlcc/src/execution/execution_strategy.h`

```cpp
// SQLCC ExecutionStrategy核心设计
class ExecutionStrategy {
public:
    // 模板方法模式：定义执行流程的标准骨架
    virtual ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) = 0;
```

#### 策略模式的工程价值体现

**1. 开闭原则(Open-Closed Principle)**
- 新增SQL语句类型只需创建新的策略类，无需修改现有代码
- SQLCC支持通过扩展添加新的SQL特性，如Window Function、Set Operation等

**2. 单一职责原则(Single Responsibility Principle)**
- 每个策略类只负责特定类型SQL语句的执行逻辑
- `DDLExecutionStrategy`专注数据定义，`DMLExecutionStrategy`专注数据操作

**3. 里氏替换原则(Liskov Substitution Principle)**
- 所有具体策略类都可以替换抽象基类使用
- `UnifiedExecutor`可以透明地切换不同的执行策略

**4. 接口隔离原则(Interface Segregation Principle)**
- 执行策略接口精确定义执行契约，避免接口污染
- 权限检查、语句验证等接口分离，职责明确

**5. 依赖倒置原则(Dependency Inversion Principle)**
- 高层模块(`UnifiedExecutor`)依赖抽象接口(`ExecutionStrategy`)
- 低层模块(具体策略)实现抽象接口，符合依赖倒置

### 4.1.3 模板方法模式在执行流程中的应用

模板方法模式(Template Method Pattern)定义了算法的骨架，将某些步骤延迟到子类实现。在SQLCC中，`UnifiedExecutor`通过模板方法模式定义了SQL语句执行的标准流程。

#### UnifiedExecutor的模板方法设计

```cpp
// SQLCC UnifiedExecutor核心设计
class UnifiedExecutor : public ExecutionStrategy {
public:
    // 模板方法：定义执行流程的标准骨架
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        // 第一步：权限预检查
        if (!checkPermission(*stmt, context)) {
            return createErrorResult("Permission denied");
        }
        
        // 第二步：语句验证
        if (!validate(*stmt, context)) {
            return createErrorResult("Statement validation failed");
        }
        
        // 第三步：策略选择和执行
        switch (stmt->getType()) {
            case Statement::SELECT:
                return executeSelect(
                    dynamic_cast<SelectStatement&>(*stmt), context);
            case Statement::INSERT:
                return executeInsert(*stmt, context);
            case Statement::UPDATE:
                return executeUpdate(*stmt, context);
            case Statement::DELETE:
                return executeDelete(*stmt, context);
            default:
                return createErrorResult("Unsupported statement type");
        }
    }
    
private:
    // 聚合引擎：聚合查询处理
    std::unique_ptr<AggregateEngine> aggregate_engine_;
    
    // 分组执行器：GROUP BY处理
    std::unique_ptr<GroupByExecutor> group_by_executor_;
    
    // 具体执行方法：由子类或组合对象实现
    ExecutionResult executeSelect(
        const SelectStatement& stmt, ExecutionContext& context);
    ExecutionResult executeInsert(
        const Statement& stmt, ExecutionContext& context);
    ExecutionResult executeUpdate(
        const Statement& stmt, ExecutionContext& context);
    ExecutionResult executeDelete(
        const Statement& stmt, ExecutionContext& context);
};
```

### 4.1.6 SQLCC架构的现代化设计理念

SQLCC的架构设计体现了现代软件工程的核心设计理念：

#### SOLID原则的完整体现

**单一职责原则(SRP)**
- `ExecutionStrategy`专门负责SQL语句执行的接口定义和管理
- `DDLExecutionStrategy`专注数据定义语言语句的执行
- `DMLExecutionStrategy`专注数据操作语言语句的执行

**开闭原则(OCP)**
- 新执行策略通过继承`ExecutionStrategy`实现，不修改现有代码
- 新SQL特性（如Window Function、Set Operation）通过扩展现有类实现

**里氏替换原则(LSP)**
- 所有执行策略都可以互相替换使用
- `UnifiedExecutor`可以透明地切换不同的执行策略

**接口隔离原则(ISP)**
- 执行策略接口精确定义执行契约
- 权限检查、语句验证等接口分离，职责明确

**依赖倒置原则(DIP)**
- 高层模块(`UnifiedExecutor`)依赖抽象接口(`ExecutionStrategy`)
- 低层模块(具体策略)实现抽象接口，符合依赖倒置

#### 设计模式的系统应用

**策略模式(Strategy Pattern)**
- `ExecutionStrategy`及其子类实现不同SQL语句的执行策略
- 运行时动态选择合适的执行策略

**模板方法模式(Template Method Pattern)**
- `UnifiedExecutor`定义执行流程的标准骨架
- 具体步骤由子类或组合对象实现

**组合模式(Composite Pattern)**
- 复杂SQL语句的AST节点采用组合模式
- 递归结构支持无限嵌套

**工厂模式(Factory Pattern)**
- `QueryPlanFactory`根据SQL类型创建相应的查询计划
- 策略选择器根据条件选择合适的执行策略

**观察者模式(Observer Pattern)**
- 执行过程的监控和事件通知
- 性能统计和日志记录

```cpp
// SQLCC DCLExecutionStrategy的核心实现
class DCLExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        // 根据DCL语句类型分发
        switch (stmt->getType()) {
            case Statement::GRANT:
                return executeGrant(
                    dynamic_cast<GrantStatement&>(*stmt), context);
            case Statement::REVOKE:
                return executeRevoke(
                    dynamic_cast<RevokeStatement&>(*stmt), context);
            default:
                return createErrorResult("Unsupported DCL statement");
        }
    }
    
private:
    // GRANT语句执行
    ExecutionResult executeGrant(
        const GrantStatement& stmt, ExecutionContext& context) {
        
        // 1. 验证执行者是否有授予权限
        if (!hasGrantPermission(context)) {
            return createErrorResult("Insufficient privileges to grant");
        }
        
        // 2. 验证目标用户是否存在
        if (!userExists(stmt.getTargetUser(), context)) {
            return createErrorResult("Target user does not exist");
        }
        
        // 3. 更新权限表
        updatePermissions(stmt.getPermissions(), stmt.getTargetUser());
        
        // 4. 记录审计日志
        logAuditEvent("GRANT", stmt.getTargetUser(), stmt.getPermissions());
        
        return createSuccessResult("Permissions granted successfully");
    }
    
    // REVOKE语句执行
    ExecutionResult executeRevoke(
        const RevokeStatement& stmt, ExecutionContext& context) {
        
        // 1. 验证执行者是否有撤销权限
        if (!hasRevokePermission(context)) {
            return createErrorResult("Insufficient privileges to revoke");
        }
        
        // 2. 从权限表中移除权限
        removePermissions(stmt.getPermissions(), stmt.getTargetUser());
        
        // 3. 记录审计日志
        logAuditEvent("REVOKE", stmt.getTargetUser(), stmt.getPermissions());
        
        return createSuccessResult("Permissions revoked successfully");
    }
};
```

```cpp
public:

                    dynamic_cast<CreateIndexStatement&>(*stmt), context);

        const CreateTableStatement& stmt, ExecutionContext& context) {

            return createErrorResult("Table already exists");

        // 2. 验证列定义的有效性
        if (!validateColumnDefinitions(stmt.getColumns())) {
            return createErrorResult("Invalid column definitions");

        // 3. 验证约束定义的有效性

            return createErrorResult("Invalid constraints");

        }

        metadata_manager_->registerTable(stmt.getTableName(), 
                                          stmt.getColumns(), 
                                          stmt.getConstraints());
        
        // 6. 记录DDL操作日志
        logDDLOperation("CREATE_TABLE", stmt.getTableName());
        
        return createSuccessResult("Table created successfully");
    }
```

```cpp
// SQLCC DMLExecutionStrategy的核心实现
class DMLExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        switch (stmt->getType()) {
            case Statement::SELECT:
                return executeSelect(
                    dynamic_cast<SelectStatement&>(*stmt), context);
            case Statement::INSERT:
                return executeInsert(
                    dynamic_cast<InsertStatement&>(*stmt), context);
            case Statement::UPDATE:
                return executeUpdate(
                    dynamic_cast<UpdateStatement&>(*stmt), context);
            case Statement::DELETE:
                return executeDelete(
                    dynamic_cast<DeleteStatement&>(*stmt), context);
            default:
                return createErrorResult("Unsupported DML statement");
        }
    }
    
private:
    // SELECT查询执行流程
    ExecutionResult executeSelect(
        const SelectStatement& stmt, ExecutionContext& context) {
        
        // 1. 查询优化
        QueryPlan plan = cost_estimator_->optimizeQuery(stmt, context);
        
        // 2. 检查查询类型
        if (requiresAggregation(stmt)) {
            // 聚合查询：使用聚合引擎
            return aggregate_engine_->executeAggregateQuery(stmt, context);
        } else if (requiresGrouping(stmt)) {
            // 分组查询：使用分组执行器
            return group_by_executor_->executeGroupBy(stmt, context);
        } else if (requiresJoin(stmt)) {
            // 连接查询：使用连接执行器
            return executeJoinSelect(stmt, context);
        } else {
            // 简单查询：直接执行
            return executeSimpleSelect(stmt, context);
        }
    }
    
    // INSERT执行流程
    ExecutionResult executeInsert(
        const InsertStatement& stmt, ExecutionContext& context) {
        
        // 1. 验证表是否存在
        if (!checkTableExists(stmt.getTableName(), context)) {
            return createErrorResult("Table does not exist");
        }
        
        // 2. 验证列定义
        if (!validateColumns(stmt.getTableName(), stmt.getColumnNames(), context)) {
            return createErrorResult("Invalid column names");
        }
        
        // 3. 执行约束验证
        if (!validateConstraints(stmt.getTableName(), stmt.getValues(), context)) {
            return createErrorResult("Constraint violation");
        }
        
        // 4. 在存储引擎中插入数据
        StorageEngineResult result = 
            storage_engine_->insertData(stmt.getTableName(), stmt.getValues());
        
        if (!result.success) {
            return createErrorResult(result.error_message);
        }
        
        // 5. 更新索引
        index_manager_->updateIndexes(stmt.getTableName(), stmt.getValues());
        
        // 6. 返回受影响的行数
        return createSuccessResult(
            std::to_string(result.rows_affected) + " row(s) inserted");
    }
};
```

## 4.3 DBMS架构设计的演进：从单机到云原生

### 5.1.1 数据库使用角色的需求分析

数据库系统服务于不同类型的用户，每类用户有不同的需求和关注点。为了满足这些差异化的需求，数据库系统设计了不同的角色和权限体系。

#### 数据库管理员(DBA)的需求

数据库管理员是数据库系统的最高管理者，他们关注的是整个数据库系统的健康运行和安全管理：

``mermaid

    A --> F[故障诊断处理]

    B --> H[授权/撤销权限]
    C --> I[角色管理]
    C --> J[访问控制]
    D --> K[数据备份]
    D --> L[灾难恢复]
    E --> M[查询优化]
    E --> N[资源配置]
    F --> O[日志分析]
    F --> P[问题定位]
```

DBA需要能够：
- 控制谁可以访问数据库（用户管理）
- 决定用户可以做什么（权限管理）
- 保护数据不被未授权访问（安全管理）
- 确保数据在意外情况下的可恢复性（备份恢复）
- 监控系统性能并进行调优（性能管理）

这些需求催生了**数据控制语言(DCL)**，专门用于管理数据库的安全和访问控制。

#### 数据库开发人员的需求

数据库开发人员负责设计和实现数据库应用，他们关注的是如何有效地定义和操作数据：

``mermaid

    B --> F[表结构设计]

    C --> J[检查约束]
    D --> K[增删改查]
    E --> L[复杂查询]
    E --> M[连接操作]
```

开发人员需要能够：
- 定义数据应该如何组织（表结构、索引等）
- 确保数据符合业务规则（约束检查）
- 实现业务逻辑所需的数据操作（增删改查）
- 编写高效的查询语句获取所需数据

这些需求催生了**数据定义语言(DDL)**用于定义数据结构，**数据操作语言(DML)**用于操作数据，以及**数据查询语言(DQL)**用于查询数据。

#### 业务用户的需求

业务用户是数据库系统的最终使用者，他们关注的是如何方便快捷地获取和操作业务数据：

``mermaid

```
- 快速查询所需数据
- 生成各种业务报表
- 录入和更新业务数据
- 执行日常业务操作

这些需求主要通过**数据查询语言(DQL)**和**数据操作语言(DML)**来满足。

基于以上不同角色的需求分析，SQL语言自然地分化为四个主要类别：

```

SELECT name, salary FROM employees WHERE salary > 5000;

-- 排序查询

-- 分组统计
SELECT department_id, AVG(salary) as avg_salary 
FROM employees 
GROUP BY department_id;

-- 多表连接
SELECT e.name, d.department_name 
FROM employees e 
JOIN departments d ON e.department_id = d.id;

-- 复杂查询
SELECT d.department_name, COUNT(e.id) as employee_count, AVG(e.salary) as avg_salary
FROM employees e
JOIN departments d ON e.department_id = d.id
WHERE e.hire_date >= '2023-01-01'
GROUP BY d.department_name
HAVING COUNT(e.id) > 5
ORDER BY avg_salary DESC
LIMIT 10;

## 5.2 DBMS对计算机科学各领域的依赖与促进

### 5.2.1 对操作系统的需求与促进

操作系统是DBMS运行的基础平台，DBMS对操作系统有着深度的依赖，同时也推动了操作系统技术的发展。

#### DBMS对操作系统的需求

``mermaid

```
1. **进程管理需求**
   - 多线程支持：DBMS需要同时处理多个用户请求，需要操作系统的多线程支持
   - 进程调度：高效的进程调度算法能提升数据库的并发处理能力
   - 资源分配：合理的CPU和内存资源分配保证系统稳定运行

   - 内存映射：通过内存映射文件技术提升I/O性能
   - 缓冲管理：操作系统提供的缓冲机制与DBMS自身的缓冲池协同工作

3. **文件系统需求**
```

## 5.2 DBMS四大语言的工程实现

### 5.2.1 DDL（数据定义语言）实现

DDL负责数据库对象的创建、修改和删除。

#### CREATE语句执行流程

1. **CREATE DATABASE**
   - 验证数据库名称是否合法
   - 检查数据库是否已存在
   - 创建数据库目录结构
   - 初始化数据库元数据

2. **CREATE TABLE**
   - 解析表定义，包括列定义和约束
   - 验证列名唯一性
   - 验证约束定义的有效性
   - 在存储引擎中创建表结构
   - 注册表元数据到目录系统
   - 创建约束执行器

#### ALTER语句执行流程

1. **ALTER DATABASE**
   - 修改数据库属性
   - 更新数据库元数据

2. **ALTER TABLE**
   - 添加/删除列
   - 添加/删除约束
   - 修改列定义
   - 重建表结构（如需要）

#### DROP语句执行流程

1. **DROP DATABASE**
   - 验证数据库是否存在
   - 删除数据库目录结构
   - 清理相关元数据

2. **DROP TABLE**
   - 验证表是否存在
   - 删除表数据和结构
   - 清理相关约束和索引
   - 从目录系统中移除表元数据

### 5.2.2 DML（数据操作语言）实现

DML负责对数据库中的数据进行操作。

#### INSERT语句执行流程

1. 解析插入数据
2. 验证表是否存在
3. 验证列数和数据类型匹配
4. 执行约束验证（主键、唯一性等）
5. 在存储引擎中插入记录
6. 更新索引（如适用）
7. 返回插入结果

#### SELECT语句执行流程

1. 解析查询条件
2. 验证表和列是否存在
3. 应用WHERE条件过滤
4. 执行排序和分组（如指定）
5. 从存储引擎获取数据
6. 格式化查询结果

#### UPDATE语句执行流程

1. 解析更新条件和新值
2. 验证表和列是否存在
3. 应用WHERE条件定位记录
4. 执行约束验证
5. 在存储引擎中更新记录
6. 更新相关索引
7. 返回更新结果

#### DELETE语句执行流程

1. 解析删除条件
2. 验证表是否存在
3. 应用WHERE条件定位记录
4. 执行约束验证（外键约束等）
5. 在存储引擎中删除记录
6. 更新相关索引
7. 返回删除结果

### 5.2.3 DCL（数据控制语言）实现

DCL负责数据库的安全性和访问控制。

#### GRANT语句执行流程

1. 验证用户是否存在
2. 验证权限类型是否有效
3. 检查执行者是否具有授予权限
4. 更新用户权限表
5. 持久化权限信息

#### REVOKE语句执行流程

1. 验证用户是否存在
2. 验证权限类型是否有效
3. 检查执行者是否具有撤销权限
4. 从用户权限表中移除权限
5. 持久化权限信息

### 5.2.4 DQL（数据查询语言）实现

DQL负责数据的查询检索。

#### 查询执行流程

1. SQL解析：将SQL语句解析为抽象语法树
2. 语义分析：验证表和列是否存在，权限检查
3. 查询优化：生成最优执行计划
4. 查询执行：按计划执行查询操作
5. 结果返回：格式化并返回查询结果

### 4.1.5 柔性架构设计：可渐进式增强的架构思路

#### 什么是柔性架构？

**定义**：柔性架构是指能够适应需求变化、技术演进和环境变化的架构设计。它不是一次性完成的，而是可以逐步增强和改进的。

**生活中的类比**：
- **城市交通系统**：从简单的道路网络，逐步扩展到高速公路、地铁、轻轨、共享单车等多层次交通系统
- **手机操作系统**：从基本的通话和短信功能，逐步扩展到智能应用、云服务、AI助手等功能

```cpp

public:
    virtual ~IStorage() = default;

    virtual bool remove(const std::string& key) = 0;

class FileStorage : public IStorage {
public:
    bool write(const std::string& key, const std::string& value) override;
    bool read(const std::string& key, std::string& value) override;
    bool remove(const std::string& key) override;
};

class DatabaseStorage : public IStorage {
public:
    bool write(const std::string& key, const std::string& value) override;
    bool read(const std::string& key, std::string& value) override;
    bool remove(const std::string& key) override;
};

    bool read(const std::string& key, std::string& value) override;
    bool remove(const std::string& key) const override;
};

// 使用接口而非具体实现
class DataManager {
public:
```

```cpp
// 通过插件系统实现功能扩展

// 插件接口
class IPlugin {
public:
    virtual ~IPlugin() = default;
    virtual std::string getName() const = 0;
    virtual bool initialize() = 0;
    virtual void shutdown() = 0;
    virtual void execute(const std::string& command) = 0;
};

// 插件管理器
class PluginManager {
public:
    bool loadPlugin(const std::string& pluginPath) {
        // 动态加载插件库
        void* handle = dlopen(pluginPath.c_str(), RTLD_LAZY);
        
        // 获取插件创建函数
        auto createPlugin = (IPlugin* (*)()) dlsym(handle, "createPlugin");
        
        // 创建插件实例
        IPlugin* plugin = createPlugin();
        
        // 初始化插件
        if (plugin->initialize()) {
            plugins_[plugin->getName()] = plugin;
            return true;
        }
        
        return false;
    }
    
    void executePlugin(const std::string& pluginName, const std::string& command) {
        if (plugins_.find(pluginName) != plugins_.end()) {
            plugins_[pluginName]->execute(command);
        }
    }
    
private:
    std::unordered_map<std::string, IPlugin*> plugins_;
};

// 用户可以创建自定义插件
class CustomAnalyticsPlugin : public IPlugin {
public:
    std::string getName() const override { return "CustomAnalytics"; }
    
    bool initialize() override {
        // 初始化插件
        return true;
    }
    
    void shutdown() override {
        // 清理插件资源
    }
    
    void execute(const std::string& command) override {
        // 执行插件功能
        if (command == "analyze") {
            performAnalytics();
        }
    }
};
```

**优势**：

```cpp
class SelectExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        auto selectStmt = dynamic_cast<SelectStatement*>(stmt.get());
        
        // SELECT语句的执行逻辑
        return executeSelect(selectStmt, context);

class UnifiedExecutor : public ExecutionStrategy {
public:
    UnifiedExecutor() {
        // 注册所有执行策略
        strategies_[Statement::SELECT] = std::make_unique<SelectExecutionStrategy>();
        strategies_[Statement::INSERT] = std::make_unique<InsertExecutionStrategy>();
        strategies_[Statement::UPDATE] = std::make_unique<UpdateExecutionStrategy>();
        strategies_[Statement::DELETE] = std::make_unique<DeleteExecutionStrategy>();
        strategies_[Statement::CREATE_TABLE] = std::make_unique<DDLExecutionStrategy>();
        strategies_[Statement::DROP_TABLE] = std::make_unique<DDLExecutionStrategy>();
    }
    
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        // 根据语句类型选择策略
        auto strategy = strategies_[stmt->getType()];
        
        // 委托给具体策略执行
        return strategy->execute(std::move(stmt), context);
    }
    
    bool checkPermission(
        const sql_parser::Statement& stmt,
        const std::ExecutionContext& context) override {
        
        // 委托给具体策略
        auto strategy = strategies_[stmt->getType()];
        return strategy->checkPermission(stmt, context);
    }
    
    bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) override {
        
        // 委托给具体策略
        auto strategy = strategies_[stmt->getType()];
        return strategy->validate(stmt, context);
    }
    
private:
    std::unordered_map<Statement::Type, 
                       std::unique_ptr<ExecutionStrategy>> strategies_;
```

```cpp
        // 动态加载插件库
        void* handle = dlopen(pluginPath.c_str(), RTLD_LAZY);
        if (!handle) {
            return false;
        }
        
        // 获取插件创建函数
        auto createPlugin = (IPlugin* (*)()) dlsym(handle, "createPlugin");

            return false;

        IPlugin* plugin = createPlugin();
        
        // 初始化插件
        if (!plugin->initialize(this)) {
            delete plugin;
            dlclose(handle);
            return false;
        }
        
        // 注册插件
        plugins_[plugin->getName()] = plugin;
        
        return true;

                      const std::string& command,
                      PluginContext* context) {
        
        auto it = plugins_.find(pluginName);
        if (it != plugins_.end()) {
            it->second->execute(command, context);
        }
    }

        auto it = plugins_.find(pluginName);
        if (it != plugins_.end()) {
            it->second->shutdown();
            delete it->second;
            plugins_.erase(it);
        }
    }
```

1. **层次数据库架构**：以早期DB2为代表
2. **现代关系型数据库架构**：以Oracle、PostgreSQL、MySQL、SQLite为代表
3. **SQLCC教育性数据库架构**：面向教学和实践的现代化设计

### A.1.1 技术环境对数据库架构设计的影响

数据库架构的设计从来不是凭空想象的，而是深深植根于当时的硬件技术水平、编译器能力、编程语言特性以及网络环境约束。理解这些技术背景，才能真正把握数据库架构演进的内在逻辑。

| **存储格式** | VSAM文件 | 磁盘优化，顺序访问 |
| **查询处理** | 预编译SQL | 编译器限制，减少运行时开销 |
| **并发控制** | 粗粒度锁 | CPU限制，简化并发管理 |
| **部署方式** | 集中式 | 网络限制，避免分布式开销 |

| **访问方式** | 直接API调用 | 无服务器，嵌入式设计 |

| **并发控制** | 锁机制 | 简单可靠，避免复杂性 |
| **部署方式** | 嵌入式库 | 移动设备，离线应用 |

### A.2 层次数据库架构：以早期DB2为例

#### A.2.1 历史背景

层次数据库（Hierarchical Database）是20世纪60年代到70年代的主流数据库模型。IBM的IMS（Information Management System）是层次数据库的典型代表，也是最早的数据库管理系统之一。

**时间线**：
```
1966年：IBM开发IMS系统（层次数据库的鼻祖）
1970年代：层次数据库广泛应用于大型机系统
1980年代：开始向关系型数据库过渡
```

#### A.2.3 核心设计特点

**1. 层次数据模型**

层次数据库采用树状结构组织数据：

```
        公司（根节点）
         │
    ┌────┴────┬────┬────┐
    ↓         ↓    ↓    ↓
  部门A    部门B 部门C 部门D
    │         │
  ┌─┴─┐     ┌─┴─┐
  ↓   ↓     ↓   ↓
员工1 员工2 员工3 员工4

特点：
- 只有一个根节点
- 子节点有且只有一个父节点
- 数据访问必须从根开始，沿层次路径向下
- 不支持多对多关系（需要冗余数据）
```

**2. 预定义的访问路径**

```cobol
           CALL 'CBLTDLI' USING GU-PCB
                                  PSB-NAME

                                  EMPLOYEE-IO-AREA
```


#### A.2.4 架构优势

1. **查询性能高**
   - 预定义的访问路径，无需动态优化
   - 适合层次结构清晰的数据访问
   - 固定的存储结构优化了I/O性能

2. **数据完整性**
   - 层次关系强制数据结构
   - 避免了数据冗余和更新异常

3. **事务处理能力强**
   - 早期实现了事务处理机制
   - 支持并发控制和恢复

#### A.2.5 架构局限性

1. **数据模型僵化**
   - 只支持层次结构，无法表示复杂关系
   - 多对多关系需要冗余存储
   - 结构变化困难

2. **查询灵活性差**
   - 必须按层次路径访问
   - 无法进行灵活的查询组合
   - 缺少数据独立性

3. **应用开发复杂**
   - 需要预定义所有访问路径
   - 嵌入式SQL需要预编译
   - 学习曲线陡峭

4. **扩展性差**
   - 无法横向扩展
   - 依赖大型机硬件
   - 成本高昂

```c
// 层次数据库的查询限制示例

// 问题：查找所有薪资高于50000的员工
// 在关系型数据库中：
SELECT * FROM employees WHERE salary > 50000;

// 在层次数据库中（非常复杂）：
// 1. 必须从公司根节点开始
// 2. 遍历所有部门
// 3. 遍历每个部门的所有员工
// 4. 逐个检查薪资条件
// 5. 无法利用索引优化非层次路径的查询
```

**Oracle架构的核心特性**：

1. **多版本并发控制（MVCC）**
   ```sql
   -- Oracle通过Undo表空间实现MVCC
   -- 读取操作不会阻塞写入操作
   -- 写入操作不会阻塞读取操作
   
   CREATE UNDO TABLESPACE undotbs1
   DATAFILE '/u01/oradata/undotbs01.dbf' SIZE 100M;
   
   -- 查询可以看到过去某个时间点的数据
   SELECT * FROM employees 
   AS OF TIMESTAMP SYSDATE - INTERVAL '1' HOUR;
   ```

2. **强大的查询优化器**
   ```sql
   -- Oracle成本优化器（CBO）考虑多种因素
   -- 表的大小、索引选择性、统计信息等
   
   -- 收集统计信息
   EXEC DBMS_STATS.GATHER_TABLE_STATS(
       ownname => 'HR',
       tabname => 'EMPLOYEES',
       estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
       method_opt => 'FOR ALL COLUMNS SIZE AUTO',
       degree => DBMS_STATS.AUTO_DEGREE
   );
   
   -- 查看执行计划
   EXPLAIN PLAN FOR
   SELECT e.last_name, d.department_name
   FROM employees e, departments d
   WHERE e.department_id = d.department_id
   AND e.salary > 5000;
   
   SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
   ```

3. **高级安全特性**
   ```sql
   -- 细粒度访问控制（FGAC）
   CREATE OR REPLACE TRIGGER secure_employees
   BEFORE SELECT ON employees
   FOR EACH ROW
   BEGIN
       IF SYS_CONTEXT('USERENV', 'SESSION_USER') != 'HR'
          AND :OLD.department_id != 
              (SELECT department_id FROM employees 
               WHERE employee_id = 
               SYS_CONTEXT('USERENV', 'SESSION_USERID'))
       THEN
           RAISE_APPLICATION_ERROR(-20001, 
               'Access denied to other departments');
       END IF;
   END;
   
   -- 数据库审计
   AUDIT ALL BY hr BY ACCESS;
   AUDIT SELECT, UPDATE ON hr.employees BY ACCESS;
   ```

4. **高可用性架构**

#### A.4.3 核心设计特点

**1. 策略模式的执行架构**

```cpp
// SQLCC的执行策略模式实现

// 抽象策略基类
class ExecutionStrategy {
public:
    virtual ~ExecutionStrategy() = default;
    
    // 执行SQL语句（纯虚函数，子类必须实现）
    virtual ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) = 0;
    
    // 权限检查
    virtual bool checkPermission(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
    
    // 参数验证
    virtual bool validate(
        const sql_parser::Statement& stmt,
        const ExecutionContext& context) = 0;
};

// SELECT语句执行策略
class SelectExecutionStrategy : public ExecutionStrategy {
public:
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        auto selectStmt = dynamic_cast<SelectStatement*>(stmt.get());
        
        // 1. 权限检查
        if (!checkPermission(*selectStmt, context)) {
            return ExecutionResult::error("Permission denied");
        }
        
        // 2. 参数验证
        if (!validate(*selectStmt, context)) {
            return ExecutionResult::error("Invalid parameters");
        }
        
        // 3. 执行SELECT查询
        return executeSelect(selectStmt, context);
    }
    
private:
    ExecutionResult executeSelect(SelectStatement* stmt, ExecutionContext& context);
};

// 统一执行器（上下文类）
class UnifiedExecutor : public ExecutionStrategy {
public:
    UnifiedExecutor() {
        // 注册所有执行策略
        strategies_[Statement::SELECT] = 
            std::make_unique<SelectExecutionStrategy>();
        strategies_[Statement::INSERT] = 
            std::make_unique<InsertExecutionStrategy>();
        strategies_[Statement::UPDATE] = 
            std::make_unique<UpdateExecutionStrategy>();
        strategies_[Statement::DELETE] = 
            std::make_unique<DeleteExecutionStrategy>();
        strategies_[Statement::CREATE_TABLE] = 
            std::make_unique<DDLExecutionStrategy>();
        strategies_[Statement::DROP_TABLE] = 
            std::make_unique<DDLExecutionStrategy>();
    }
    
    ExecutionResult execute(
        std::unique_ptr<sql_parser::Statement> stmt,
        ExecutionContext& context) override {
        
        // 根据语句类型选择策略
        auto strategy = strategies_[stmt->getType()];
        
        // 委托给具体策略执行
        return strategy->execute(std::move(stmt), context);
    }
    
private:
    std::unordered_map<Statement::Type, 
                       std::unique_ptr<ExecutionStrategy>> strategies_;
};
```

```
1. 性能 vs 灵活性

│  性能优先：                                    │

│  - 固定存储结构                                │
│  - 专用查询语言                                │

│                                                 │
│  灵活性优先：                                  │
│  - 动态查询优化（关系型数据库）                │
│  - 灵活的数据模型                              │
│  - 标准查询语言                                │
│  → 适合需求多变的应用                          │
└─────────────────────────────────────────────────┘

2. 一致性 vs 可用性
┌─────────────────────────────────────────────────┐
│  一致性优先（CP）：                             │
│  - 强一致性保证                                │
│  - 分区时不可用                                │
│  - 传统关系型数据库                            │
│  → 适合金融、交易系统                          │
│                                                 │
│  可用性优先（AP）：                             │
│  - 最终一致性                                  │
│  - 分区时仍可用                                │
│  - NoSQL数据库                                 │
│  → 适合互联网应用                              │
└─────────────────────────────────────────────────┘

3. 复杂性 vs 功能性
┌─────────────────────────────────────────────────┐
│  简单性优先：                                  │
│  - 功能精简                                    │
│  - 易于理解                                    │
│  - 快速开发                                    │
│  → SQLite、SQLCC                               │
│                                                 │
│  功能性优先：                                  │
│  - 功能全面                                    │
│  - 企业级特性                                  │
│  - 复杂度高                                    │
│  → Oracle、DB2                                 │
└─────────────────────────────────────────────────┘

4. 性能 vs 成本
┌─────────────────────────────────────────────────┐
│  性能优先：                                    │
│  - 内存数据库                                  │
│  - 分布式集群                                  │
│  - 高性能硬件                                  │
│  → 成本高昂                                    │
│                                                 │
│  成本优先：                                    │
│  - 开源数据库                                  │
│  - 单机部署                                    │
│  - 标准硬件                                    │
│  → 性能相对较低                                │
└─────────────────────────────────────────────────┘
```

#### A.8.2 思考题

1. **架构设计权衡**：
   - 为什么早期数据库采用层次模型而不是关系模型？
   - 关系模型在哪些方面优于层次模型？又有哪些劣势？
   - 如果你要设计一个高性能的嵌入式数据库，你会选择哪种架构？

2. **性能优化策略**：
   - Oracle和MySQL在查询优化方面有哪些共同点和不同点？
   - 缓存策略如何影响数据库性能？有哪些权衡？
   - 在分布式环境下，如何平衡性能和一致性？

3. **安全性设计**：
   - 商业数据库如何保障数据安全？有哪些安全机制？
   - 细粒度访问控制（FGAC）如何实现？有什么优势？
   - 在云环境下，数据安全面临哪些新挑战？

4. **分布式架构**：
   - CAP定理对分布式数据库设计有什么影响？
   - 两阶段提交（2PC）和三阶段提交（3PC）有什么区别？
   - 如何实现高可用的分布式数据库？

5. **架构演进**：
   - 数据库架构从层次模型到关系模型，再到NoSQL，演进的核心驱动力是什么？
   - 未来数据库架构会如何发展？有哪些技术趋势？
   - SQLCC如何借鉴现代数据库的设计思想？
