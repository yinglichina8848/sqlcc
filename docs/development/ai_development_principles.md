# AI开发原则

## 项目目录结构管理原则

### 1. 主目录整洁原则
- **禁止在主目录下执行代码生成、编译和测试运行**
- 所有生存、调试和测试文件必须放置在对应的子目录中
- 主目录仅保留项目核心配置文件、文档和顶层构建定义

### 2. 测试文件组织原则
- 所有调试文件必须放置在 `tests/components/debug/` 目录下
- 所有性能测试文件必须放置在 `tests/performance/` 目录下
- 测试文件必须通过Bazel测试体系进行集成和管理

### 3. Bazel集成原则
- 所有测试必须通过Bazel构建系统进行管理
- 测试文件必须定义在对应的BUILD.bazel配置文件中
- 测试套件必须通过test_suite进行组织和管理

### 4. 文件移动和清理原则
- 定期检查主目录，将生成的测试文件和调试文件移动到对应目录
- 移动文件后必须更新相应的Bazel配置文件
- 确保主目录保持整洁，便于项目维护和管理

## 实施指南

### 新文件创建
- 调试文件：创建在 `tests/components/debug/` 目录
- 性能测试：创建在 `tests/performance/` 目录  
- 单元测试：创建在对应的 `tests/components/` 子目录

### 现有文件整理
- 定期运行文件整理脚本检查主目录
- 将发现的生存和调试文件移动到对应目录
- 更新Bazel配置文件以集成移动的文件

### 构建和测试
- 所有构建和测试操作必须在构建目录中进行
- 使用Bazel命令运行测试：`bazel test //tests/...`
- 禁止在主目录直接编译或运行测试

## 内存安全原则

### 1. 智能指针使用原则

#### 1.1 所有权语义选择
- **std::unique_ptr**: 用于独占所有权的资源管理
  - 文件句柄、套接字、网络连接
  - 动态分配的内存块
  - 不可共享的系统资源

- **std::shared_ptr**: 用于共享所有权的资源管理
  - 缓冲池中的页面对象
  - 缓存的数据结构
  - 需要在多个组件间共享的对象

- **std::weak_ptr**: 用于打破循环引用
  - 观察者模式中的观察者对象
  - 缓存中的弱引用

#### 1.2 智能指针设计模式
```cpp
// 正确：工厂函数返回智能指针
class BufferPool {
public:
  static std::shared_ptr<BufferPool> Create(DiskManager* disk_manager,
                                           size_t pool_size) {
    return std::make_shared<BufferPool>(disk_manager, pool_size);
  }

private:
  BufferPool(DiskManager* disk_manager, size_t pool_size);
  // 私有构造函数，确保只能通过工厂函数创建
};

// 错误：直接暴露裸指针
class BufferPool {
public:
  BufferPool* CreateInstance() { // 不要这样做
    return new BufferPool();
  }
};
```

#### 1.3 智能指针传递准则
- **函数参数**: 优先使用 `const std::shared_ptr<T>&` 或 `std::weak_ptr<T>`
- **返回值**: 总是返回智能指针，避免返回裸指针
- **成员变量**: 使用智能指针存储需要管理生命周期的对象

```cpp
// 推荐写法
void ProcessPage(std::shared_ptr<Page> page) {
  // 处理页面
}

std::shared_ptr<Page> GetPage(int32_t page_id) {
  return page_table_[page_id]; // 返回智能指针
}

// 不推荐写法
void ProcessPage(Page* page) { // 裸指针，调用者需要管理生命周期
  // 处理页面
}

Page* GetPage(int32_t page_id) { // 返回裸指针，调用者负责释放
  return page_table_[page_id].get();
}
```

#### 1.4 避免智能指针滥用
- **局部变量**: 对于生命周期明确的局部对象，使用栈分配
- **性能敏感代码**: 在热点路径上评估智能指针开销
- **循环引用**: 使用 `std::weak_ptr` 打破循环引用

### 2. RAII 资源管理原则

#### 2.1 RAII 封装设计
- **资源获取即初始化**: 在构造函数中获取资源，在析构函数中释放
- **异常安全**: 确保在异常情况下资源正确释放
- **不可复制**: 对于独占资源，使用 `= delete` 要用复制操作

```cpp
class FileDescriptor {
public:
  explicit FileDescriptor(int fd) : fd_(fd) {}
  ~FileDescriptor() {
    if (fd_ >= 0) {
      ::close(fd_);
    }
  }

  // 要用复制，避免双重释放
  FileDescriptor(const FileDescriptor&) = delete;
  FileDescriptor& operator=(const FileDescriptor&) = delete;

  // 支持移动语义
  FileDescriptor(FileDescriptor&& other) noexcept : fd_(other.fd_) {
    other.fd_ = -1;
  }

private:
  int fd_;
};
```

#### 2.2 系统资源封装
- **文件描述符**: 封装 `open()`/`close()` 操作
- **网络套接字**: 封装 `socket()`/`bind()`/`listen()`/`accept()`/`close()`
- **内存映射**: 封装 `mmap()`/`munmap()` 操作
- **互斥锁**: 封装 `pthread_mutex_init()`/`pthread_mutex_destroy()`

#### 2.3 RAII 卫哨模式
```cpp
class MutexGuard {
public:
  explicit MutexGuard(std::mutex& mutex) : mutex_(mutex) {
    mutex_.lock();
  }

  ~MutexGuard() {
    mutex_.unlock();
  }

  // 要用复制
  MutexGuard(const MutexGuard&) = delete;
  MutexGuard& operator=(const MutexGuard&) = delete;

private:
  std::mutex& mutex_;
};

// 使用示例
void ThreadSafeFunction() {
  MutexGuard guard(mutex_); // 自动加锁
  // 执行线程安全操作
  // 函数返回时自动解锁
}
```

### 3. 内存管理最佳实践

#### 3.1 禁止手动内存管理
- **永远不要使用**: `new`/`delete`, `malloc`/`free`
- **例外情况**: 性能极致优化的特定场景，必须有详细注释和审计

#### 3.2 容器使用原则
- **首选标准容器**: `std::vector`, `std::string`, `std::unordered_map`
- **避免裸数组**: 使用 `std::array` 或 `std::vector` 替代 `T[]`
- **智能指针容器**: 使用 `std::vector<std::shared_ptr<T>>` 而非裸指针

#### 3.3 异常安全保证
- **强异常保证**: 操作要么完全成功，要么完全回滚
- **RAII 配合**: 使用 RAII 确保资源在异常情况下正确释放
- **智能指针**: 自动处理异常情况下的内存释放

### 4. 并发安全原则

#### 4.1 锁管理准则
- **最小化锁粒度**: 只在必要时持有锁
- **避免死锁**: 使用固定的锁顺序，或使用 `std::lock()`
- **超时机制**: 为锁操作设置合理的超时时间

```cpp
// 推荐：带超时的锁获取
std::unique_lock<std::timed_mutex> lock(latch_, std::defer_lock);
if (!lock.try_lock_for(std::chrono::milliseconds(5000))) {
  // 超时处理，避免永久阻塞
  return false;
}
```

#### 4.2 数据竞争防护
- **原子操作**: 对共享变量使用 `std::atomic`
- **内存屏障**: 在必要时使用内存屏障确保顺序
- **不可变对象**: 对于只读共享数据，考虑使用不可变对象

### 5. 错误处理原则

#### 5.1 异常使用准则
- **异常层次**: 定义清晰的异常层次结构
- **RAII 配合**: 异常不会阻止资源释放
- **异常安全**: 确保异常不会导致资源泄漏或状态不一致

#### 5.2 错误码 vs 异常
- **异常**: 用于程序错误和不可恢复的情况
- **错误码**: 用于可预期的错误情况
- **混合使用**: 根据具体场景选择合适的错误处理机制

### 6. 性能优化原则

#### 6.1 零开销抽象
- **智能指针**: 在非性能关键路径上使用智能指针
- **RAII**: RAII 封装不应带来运行时开销
- **内联优化**: 对关键函数使用 `inline` 提示

#### 6.2 内存布局优化
- **缓存对齐**: 重要数据结构使用 `alignas` 对齐
- **内存局部性**: 将相关数据放在一起，减少缓存未命中
- **对象池**: 对于频繁分配/释放的小对象，使用对象池

### 7. 代码组织原则

#### 7.1 接口设计
- **Pimpl 模式**: 隐藏实现细节，减少编译依赖
- **工厂模式**: 使用工厂函数创建对象，返回智能指针
- **依赖注入**: 通过构造函数注入依赖，便于测试

#### 7.2 模块化设计
- **单一职责**: 每个类只负责一个明确的功能
- **依赖倒置**: 依赖抽象而非具体实现
- **接口隔离**: 提供最小化的接口，避免不必要的依赖

### 8. 测试原则

#### 8.1 内存安全测试
- **ASan/LSan**: 启用地址/泄漏检测器进行测试
- **Valgrind**: 使用 Valgrind 进行详细的内存检查
- **单元测试**: 为每个 RAII 类编写完整的单元测试

#### 8.2 并发测试
- **线程安全测试**: 测试多线程环境下的正确性
- **死锁检测**: 使用工具检测潜在的死锁情况
- **竞态条件**: 编写测试暴露竞态条件

### 9. 实施指南

#### 9.1 代码审查清单
- [ ] 是否使用了智能指针而非裸指针？
- [ ] 是否正确实现了 RAII 模式？
- [ ] 是否避免了循环引用？
- [ ] 是否正确处理了异常安全？
- [ ] 是否有内存泄漏风险？

#### 9.2 重构步骤
1. **识别问题**: 使用工具检测内存问题
2. **设计方案**: 为每个资源设计 RAII 封装
3. **逐步重构**: 从叶子类开始，逐步向上重构
4. **测试验证**: 每个重构步骤后运行完整测试套件
5. **性能调优**: 监控重构后的性能影响

#### 9.3 工具使用
- **编译器警告**: 启用所有内存相关警告
- **静态分析**: 使用 Clang Static Analyzer
- **动态分析**: 使用 Valgrind, ASan, LSAN
- **代码覆盖**: 确保测试覆盖所有内存管理路径

### 头文件引用原则
- 不要使用 #include "../../../include/xxx.h" ，而是使用 #include "include/xxx.h" 的方式，保持代码的简洁和可维护性。用 -I 参数指定include目录，这样，就可以使用 #include "xxx.h" 的方式引用头文件了。
- 所有的头文件不在源码目录下，在 项目主目录的 include 目录下，记住这个原则进行查找和修改
- 不要随意自行创建头文件，除非进行新部件和类的设计和开发，测试程序所使用的核心代码和头文件都是应当存在的，只是重新整理了目录结构，进行了移动，认真查找，

## 工作日记完整性原则

### 1. 原始记录全面性
**工作日记必须记录所有开发活动的完整过程，不能删简压缩**

#### 1.1 时间线连续性
- **完整记录**: 保持完整的时间线记录，从开始到结束的所有步骤
- **不可删减**: 禁止删除或修改已有的工作记录，只能增加新记录
- **过程完整**: 记录所有问题发现、分析、解决方案和验证步骤

#### 1.2 层次修复记录
- **分层记录**: 对于分层修复（如bottom-up重构），必须记录每一层的详细修复过程
- **依赖关系**: 记录包间依赖关系和构建顺序的变化
- **状态跟踪**: 实时更新修复状态和验证结果

#### 1.3 变更记录完整性
- **修改记录**: 所有代码修改、配置调整都必须详细记录
- **问题追踪**: 记录发现的问题、分析过程和解决方案
- **验证记录**: 记录每次修改后的验证结果和测试状态
- **时间戳要求**: 每个工作记录必须包含具体的日期时间，精确到秒

#### 1.4 记录修改原则
- **只能添加**: 工作日记只能添加新记录，不能修改或删除现有内容
- **顺序记录**: 按时间顺序记录所有开发活动
- **实时更新**: 工作完成后立即记录，不能延迟

#### 1.5 工作记录与计划区分
- **工作日记**: 记录具体的任务完成情况和改进结果，只能添加不能修改
- **TODO清单**: 记录计划和计划执行现状，可以根据明确命令修改计划内容
- **一般继续命令**: 只更新TODO中的任务完成状态，不修改计划内容
- **明确修改命令**: 只有明确的修改命令才能改变TODO中的计划内容

#### 1.6 完整性保障机制
- **原始记录保护**: 所有历史工作记录永久保存，不得清理或修改
- **版本追溯**: 每个版本的工作记录必须完整且可追溯
- **系统性记录**: 确保从过去到现在的完整开发过程都有记录

### 2. TODO状态管理原则
**TODO只能更新完成状态，不能大量删除已经完成的内容**

#### 2.1 状态更新准则
- **完成标记**: 只允许将TODO项标记为完成（[x]）
- **禁止删除**: 不得删除已完成的TODO项
- **历史保留**: 保持TODO的历史记录，便于回顾

#### 2.2 进度追踪
- **实时更新**: 工作完成后立即更新TODO状态
- **状态同步**: TODO状态必须与工作日记保持同步
- **完成验证**: 只有通过验证的修改才能标记为完成

### 3. 文档管理原则
**ChangeLog和ReleaseNote可以进行总结和浓缩，但工作日记必须保持原始完整性**

#### 3.1 文档分层
- **工作日记**: 完整的时间线原始记录，不得删简
- **变更日志**: 可以总结和浓缩，便于快速浏览
- **发布说明**: 可以浓缩核心改进点，面向用户

#### 3.2 记录保留
- **永久保存**: 所有工作记录永久保存，不得清理
- **版本关联**: 明确标注每个记录所属的版本
- **可追溯性**: 确保所有修改都有完整的追溯链

## 代码重构原则

### 1. 代码完整性原则
**绝对禁止精简代码实现，不允许修改原有代码的核心逻辑**

#### 1.1 代码分离准则
- **保持完整实现**: 代码分离时必须保留所有原有功能和逻辑
- **禁止功能简化**: 不得删除或简化任何业务逻辑、错误处理或边界条件
- **原样迁移**: 代码从一个位置移动到另一个位置时，必须完全保持原有实现

#### 1.2 重构安全原则
- **功能等价性**: 重构后的代码必须与原代码在功能上完全等价
- **性能保持**: 重构不得影响原有性能特征
- **接口兼容**: 公共接口必须保持向后兼容

#### 1.3 质量保证措施
- **逐行审查**: 对分离的每行代码进行审查，确保没有遗漏
- **功能测试**: 重构后必须通过所有原有测试用例
- **回归测试**: 执行完整的回归测试套件验证功能正确性

### 2. 重构实施指南

#### 2.1 代码分离步骤
1. **完整复制**: 先完整复制所有相关代码
2. **依赖分析**: 分析并处理所有依赖关系
3. **接口调整**: 调整类和函数的访问级别
4. **构建配置**: 更新构建系统配置
5. **测试验证**: 运行完整测试验证功能

#### 2.2 质量检查清单
- [ ] 所有原代码行都被正确迁移
- [ ] 所有成员变量和方法都被保留
- [ ] 所有错误处理逻辑都被保持
- [ ] 所有注释和文档都被迁移
- [ ] 所有依赖关系都被正确处理

#### 2.3 禁止操作列表
- ❌ 删除任何业务逻辑代码
- ❌ 简化或修改算法实现
- ❌ 移除错误处理代码
- ❌ 改变数据结构定义
- ❌ 修改常量或配置值

### 3. 重构验证流程

#### 3.1 自动化验证
- **编译检查**: 确保所有代码能够成功编译
- **链接检查**: 验证所有符号链接正确
- **运行时测试**: 执行功能测试验证行为正确性

#### 3.2 人工审查
- **代码对比**: 对比原代码和重构后代码的差异
- **逻辑审查**: 审查关键算法和业务逻辑的完整性
- **性能评估**: 评估重构对性能的影响

## AI Agent 协作开发变更记录

### 变更记录目的
本节记录项目开发过程中的所有重要变更，帮助多个AI Agent协同工作，实现快速迭代式开发。每个变更记录包含：
- 变更时间和版本
- 变更内容描述
- 涉及的文件
- 变更原因和影响
- 测试验证状态

### 版本管理原则
- **主版本号**: 重大架构变更时递增 (X.0.0)
- **次版本号**: 功能新增时递增 (1.X.0)
- **修订号**: 缺陷修复时递增 (1.1.X)
- **开发迭代**: 每日开发使用日期标记 (1.1.3-YYYYMMDD)

### 变更记录格式
```
[YYYY-MM-DD HH:MM] v1.1.3-变更序号
变更类型: [FEATURE|BUGFIX|REFACTOR|DOC|TEST]
变更范围: [CORE|STORAGE|NETWORK|PARSER|EXECUTOR|TEST|DOC]

变更内容:
- 具体变更描述
- 涉及的文件列表
- 修改的函数/类

变更原因:
- 为什么要做这个变更
- 解决的问题或改进的目标

影响评估:
- 对现有功能的影响
- 性能影响
- 兼容性影响

测试验证:
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 性能测试通过
- [ ] 回归测试通过
```

### 协作开发指南#### 1. 变更记录维护
- **实时记录**: 每个重要变更都要及时记录到此文档
- **详细描述**: 包含变更原因、影响和测试状态
- **版本标记**: 使用统一的版本号和时间戳格式

#### 2. 代码审查清单
在提交变更前，检查以下项目：
- [ ] 变更已记录到此文档
- [ ] 遵循内存安全原则
- [ ] 代码通过所有测试
- [ ] 文档已相应更新
- [ ] 与其他AI Agent的变更无冲突

#### 3. 冲突解决机制
当多个AI Agent同时开发时：
1. 检查变更记录，了解其他Agent的工作
2. 在开始新任务前同步最新代码
3. 如有冲突，通过变更记录协商解决
