# SQLCC 并发控制设计文档

## 1. WHY: 为什么要进行并发控制？

在多用户数据库环境中，多个事务可能同时尝试访问和修改同一份数据。如果没有并发控制，将导致以下问题：
*   **丢失更新**: 两个事务同时修改同一行，后提交的覆盖了先提交的。
*   **脏读**: 一个事务读取了另一个尚未提交事务修改的数据。
*   **不可重复读**: 一个事务内两次读取同一数据得到不同结果。
*   **幻读**: 一个事务内两次范围查询得到不同的记录集。

并发控制的目标是实现**事务隔离性 (Isolation)**，确保并发执行的结果与某种串行执行的结果一致。

## 2. WHAT: SQLCC 并发控制架构

SQLCC 采用了**混合并发控制策略**，结合了两阶段锁协议 (2PL) 和多版本并发控制 (MVCC)。

### 核心组件：
1.  **Hierarchical Lock Manager (层级锁管理器)**:
    *   管理不同粒度的锁（表锁、页锁、行锁）。
    *   支持 **S (共享锁)** 和 **X (排他锁)**。
    *   实现 **意向锁 (Intention Locks)**，用于高效处理锁冲突。
2.  **MVCC (多版本并发控制) 引擎**:
    *   通过为数据保留多个版本，实现“读不阻塞写，写不阻塞读”。
    *   使用**快照隔离 (Snapshot Isolation)**。
3.  **Deadlock Detector (死锁检测器)**:
    *   定期扫描“等待图” (Wait-for Graph)。
    *   发现环路时，选择一个“牺牲者”事务进行回滚。
4.  **Transaction Context (事务上下文)**:
    *   跟踪每个事务持有的所有锁，以便在提交或回滚时统一释放。

## 3. HOW: 核心协议与实现机制

### 3.1. 严格两阶段锁协议 (Strict 2PL)
SQLCC 遵循严格的 2PL：
1.  **增长阶段**: 事务执行过程中根据需要获取锁。
2.  **持有阶段**: 事务在未结束前不能释放任何锁。
3.  **释放阶段**: 事务提交或回滚后，**一次性释放所有锁**。
*   **WHY**: 严格 2PL 能够彻底避免脏读，并简化回滚逻辑。

### 3.2. 锁兼容性矩阵 (Lock Compatibility)

| 持有 \ 请求 | S (读) | X (写) |
| :--- | :---: | :---: |
| **S (读)** | 兼容 | 冲突 |
| **X (写)** | 冲突 | 冲突 |

### 3.3. 多版本可见性判断 (MVCC Visibility)
每个记录包含两个隐藏列：`xmin` (创建该版本的事务 ID) 和 `xmax` (删除该版本的事务 ID)。
*   **可见条件**: 对于事务 T，一个版本可见当且仅当：
    1.  `xmin` 已提交且 `xmin < T.id`。
    2.  `xmax` 未设置，或者 `xmax` 是由尚未提交或晚于 T 提交的事务设置的。

### 3.4. 死锁检测算法
1.  构建 **等待图**: 节点是事务，边 `T1 -> T2` 表示 T1 正在等待 T2 释放锁。
2.  运行 **DFS (深度优先搜索)**。
3.  **牺牲者选择策略**: 优先选择事务年龄最轻、持有锁最少、或尚未写入太多数据的事务回滚，以最小化系统开销。

## 4. 关键工作流程

### 4.1. 写入操作流程 (UPDATE/INSERT)
1.  事务申请目标页面的 **X 锁**。
2.  若已有其他事务持有锁，进入等待队列并启动超时计数。
3.  获取锁后，在 MVCC 引擎中创建新版本。
4.  记录写入 LSN (WAL)。
5.  事务结束后释放 X 锁。

### 4.2. 锁升级 (Lock Upgrade)
*   如果一个事务已经持有 S 锁，并尝试进行写操作，它可以申请升级为 X 锁。
*   注意：如果两个事务同时尝试升级同一资源的锁，将直接触发死锁保护。

## 5. 性能优化特性

*   **锁分片 (Lock Sharding)**: 锁表被划分为多个桶，减少全局锁竞争。
*   **无锁读 (Lock-free Reads)**: 在 READ COMMITTED 级别下，利用 MVCC 实现完全不需要加锁的快照读。
*   **智能预取 (Prefetching)**: `Prefetcher` 组件分析事务的访问模式，在锁申请间隙提前将可能需要的页面载入缓冲池。
