## 1. 执行摘要

### 1.1 背景

S05 Execution Strategy 重构项目自启动以来，面临严重的范围失控和"修复风暴"风险。当前已识别的问题包括：
- Gate-L2 编译失败：UserManager 命名空间问题 (20+ errors)
- Gate-L3 编译失败：createErrorResult 缺失、InsertRecord 参数不匹配
- 多个子任务（S05A/B/C/D/E）之间存在复杂的依赖关系

### 1.2 核心问题

当前 S05 项目存在以下根本性问题：

| 问题类别 | 问题描述 | 影响程度 |
|---------|---------|---------|
| 管理层面 | 任务分解粒度不当 | 高 |
| 流程层面 | 验证顺序错误 | 高 |
| 技术层面 | 代码债务积累 | 中 |
| 协作层面 | Agent 职责不明确 | 低 |

### 1.3 建议方案

采用 **"最小化修复 + Skills 持续管理"** 策略：

1. **短期目标（1-2天）**：快速修复阻塞性问题，让 Gate 验证通过
2. **中期目标（持续）**：用 Skills 系统追踪技术债务，按优先级逐步解决
3. **长期目标**：架构优化，统一接口契约

|------|------|--------|---------|------|

### 2.3 根本原因分析

#### 2.3.1 管理层面

**问题**：任务分解粒度不当

**表现**：
- S05 被分解为多个子任务，但每个任务的边界不清晰
- 新的问题不断涌现，任务列表持续扩展
- 缺乏整体目标定义，导致"做一步看一步"

**影响**：
- 难以评估项目进度
- 容易遗漏关键依赖
- 修复工作可能引入新问题

#### 2.3.2 流程层面

**问题**：验证顺序错误

**表现**：
- 先进行设计（S05C），后进行验证（Gate L1/L2/L3）
- 设计时未考虑已知的编译问题
- 验证时不断发现新问题，导致循环

**影响**：
- 设计无法落地（编译不通过）
- 信心受挫（总是发现新问题）
- 进度难以预测

#### 2.3.3 技术层面

**问题**：代码债务积累

**表现**：
- 历史代码缺乏接口契约
- 命名空间管理混乱
- 函数声明与实现不一致

**影响**：
- 修复 A 问题可能触发 B 问题
- 难以进行增量修改
- 回归风险高

#### 2.3.4 协作层面

**问题**：Agent 职责不明确

**表现**：
- Claude/Gemini/OpenCode 的职责边界模糊
- 任务分配临时决定
- 缺乏统一的协作协议

**影响**：
- 工作重复或遗漏
- 沟通成本高
- 决策效率低

#### 3.1.3 工作流定义 (s05-workflow.md)

**核心原则**：

```
在开始任何子任务之前，必须先完成：
1. 总体目标定义
2. 完整依赖分析
3. 验证顺序规划
```

**验证顺序（重要！）**：

```bash
# Step 1: 全量验证
bazel build //... 2>&1 | tee issues.log

# Step 2: 问题分类
grep -E "error:|warning:" issues.log

# Step 3: 分批修复
# P0: 阻塞性问题
# P1: 次要问题
# P2: 技术债务

# Step 4: 逐批验证
bazel build //... 2>&1 | grep -E "error:|BUILD"
```

#### 3.1.4 任务分解 (s05-task-decomposition.md)

| 任务 ID | 范围 | 前置条件 | 验收标准 |
|---------|------|---------|---------|
| S05D | UserManager 命名空间修复 | 无 | Gate-L2 PASS |
| S05E | createErrorResult 声明 | 无 | Gate-L3 PASS |
| S05C | 架构设计（修订） | S05D+S05E | 双评审 PASS |
| S05X | 集成验证 | S05C | L1/L2/L3 全 PASS |

#### 3.1.5 依赖分析 (s05-dependencies.md)

**关键依赖链**：

```
execution_result.h (createErrorResult)
    ↓
dml/ddl_execution_strategy.cpp (调用)
    ↓
core_database_manager.h (查询方法)
    ↓
user_manager.h (UserManager 类)
    ↓
user_manager.cpp (命名空间问题)
```

**修复优先级**：

| 优先级 | 文件 | 修复方案 |
|--------|------|---------|
| P0 | execution_result.h | 添加 createErrorResult 声明 |
| P0 | user_manager.cpp | 添加 using 声明 |
| P1 | dml_execution_strategy.cpp | 修复 InsertRecord 参数 |
| P2 | core_database_manager.h | 添加查询方法声明 |

### 3.2 执行方案对比

#### 3.2.1 方案 A：最小化修复（推荐）

**目标**：快速让 Gate 验证通过，不追求完美

**步骤**：
1. 修复 UserManager 命名空间（最小改动）
2. 声明 createErrorResult（最简方案）
3. 修复 InsertRecord 参数（仅编译通过）

**优点**：
- ✅ 快速恢复开发流程
- ✅ 风险可控
- ✅ 避免无限延期

**缺点**：
- ❌ 可能积累技术债务
- ❌ 长期维护成本高

**适用场景**：时间紧迫，需要快速恢复开发

#### 3.2.2 方案 B：完整重构

**目标**：彻底解决所有架构问题

**步骤**：
1. 暂停所有子任务
2. 重新设计整体架构
3. 一次性修复所有问题

**优点**：
- ✅ 解决根本问题
- ✅ 长期收益高
- ✅ 架构更清晰

**缺点**：
- ❌ 耗时长
- ❌ 可能引入新问题
- ❌ 需要更多资源

**适用场景**：有充足时间，追求架构完美

## 4. 推荐方案

### 4.1 立场声明

**推荐采用方案 A（最小化修复）+ Skills 持续管理**

**理由**：
1. **时间考量**：S05 已消耗大量时间，需要快速产出
2. **风险控制**：最小改动减少引入新问题的风险
3. **可持继性**：Skills 系统可以持续追踪技术债务
4. **渐进改进**：不追求一步到位，而是逐步优化

### 4.2 执行计划

#### Phase 1：紧急修复（0-2天）

## 5. 风险评估

### 5.1 风险矩阵

| 风险 | 可能性 | 影响 | 风险等级 | 缓解措施 |
|------|--------|------|---------|----------|
| 发现更多编译错误 | 高 | 大 | 🔴 | 先全量验证，记录所有问题 |
| 修复引入回归 | 中 | 大 | 🟡 | 每个修复单独验证 |
| 任务范围失控 | 中 | 中 | 🟡 | Skills 追踪，范围控制 |
| 时间不足 | 高 | 中 | 🟡 | 最小化修复，快速产出 |
| Agent 协作不畅 | 低 | 中 | 🟢 | 明确职责，使用 Skills |

### 5.2 缓解措施

#### 5.2.1 范围控制

```
每个任务必须包含：
1. 明确的目标（做什么）
2. 明确的边界（不做什么）
3. 明确的依赖（前置条件）
4. 明确的验收（通过标准）
```

#### 5.2.2 及时止损机制

```
如果出现以下情况，立即暂停并汇报：
1. 任务范围失控
2. 发现大量未知问题（>10个）
3. 修复成本超出预估（>2倍）
4. 引入新的阻塞性问题

汇报内容：
- 当前进度
- 发现的问题
- 建议的调整方案
```
